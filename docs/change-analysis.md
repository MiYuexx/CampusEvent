# 需求变更影响分析（change-v2）

> 本版本在 `baseline-v1` 基础上创建 `change-v2` 分支实现，未删除项目重建；原有直接报名、审核报名行为保持不变。

## 1. 变更登记

| 字段 | 内容 |
| --- | --- |
| 变更编号 | CR-01、CR-02 |
| CR-01 描述 | 新增“年级限定直接报名”规则：Student 新增 grade（1—4），仅大二、大三（grade∈{2,3}）可报此类活动；仍遵守名额、活动时间、重复报名等公共约束 |
| CR-02 描述 | 站内消息之外新增模拟邮件通知：报名通过、审核通过/拒绝同时记录邮件；邮件失败留痕不回滚报名；同一业务事件不重复发送 |
| 提出时间 | 2026-11-26 |
| 对应版本标签 | change-v2 |

## 2. 受影响模块

| 层次 | 涉及类/接口/数据库对象 | 影响说明 |
| --- | --- | --- |
| 策略层 | `RegistrationPolicy`、`DirectPolicy`、`ReviewPolicy`、新增 `GradeDirectPolicy`、`factory.py` | 策略接口增加可选 `student` 参数；新增年级限定策略；原有两种策略行为不变 |
| 通知层 | `EventDispatcher`、`EventObserver`、`MessageObserver`、新增 `MockEmailSender`、`MailObserver`、`mail_log` 表 | 新增邮件订阅者与模拟发送器；站内通知保留；邮件失败写入 `mail_log` 不抛出 |
| 业务层 | `RegistrationService` | 补充学生年级读取/写入、邮件发送器注入入口；核心报名与审批流程未堆叠规则判断 |
| 数据层 | `student.grade` 字段、`mail_log` 表；`activity.policy_type` 枚举增加 `GRADE_DIRECT` | 旧库通过迁移补充 `grade` 列；新增邮件日志表 |
| 接口层 | `routes.py`：注册接口增加 `grade` 入参；新增 `/api/mails/<student_id>` 查询邮件日志 | 前端后端本地运行时可扩展展示；静态演示页未改动 |

## 3. 设计决策

### CR-01：新增独立策略，不修改核心服务流程

- 选择新增 `GradeDirectPolicy` 实现 `RegistrationPolicy`，把年级判断封装在策略内部；`RegistrationService` 只负责公共的重复报名、名额校验，并把学生信息传给策略。
- 理由：年级限定是“报名规则”的变化，与直接/审核报名属于同一扩展点；新增策略符合开闭原则，核心报名流程不需要为年级规则增加 `if/else`。
- 代价：策略接口签名需要携带学生上下文；若未来出现更多学生属性限制，可进一步组合规则对象，避免策略类膨胀。

### CR-02：观察者扩展邮件渠道，业务与投递解耦

- 新增 `MailObserver` 订阅同一事件分发器，与 `MessageObserver` 并行工作；邮件发送由 `MockEmailSender` 模拟，记录收件人、主题、内容、状态、时间与错误。
- 邮件异常在观察者内捕获并落库，不向 `RegistrationService` 抛出，避免通知故障回滚已成功提交的报名。
- 查重维度：学生 + 活动 + 主题 + 内容，防止同一业务事件重复发送；重复审批被业务层拦截，也不会产生第二份相同通知。

## 7. 反思结论

- **模式收益**：CR-01 作为新策略接入，没有在主流程中加年级分支；CR-02 作为新观察者接入，业务代码不需要知道邮件如何投递。两类变更都符合初始设计的扩展方向。
- **模式成本**：策略接口需要携带学生上下文，观察者链路比直接写消息表更长；小需求下抽象成本可见，但在本次两类变更同时出现时，扩展边界清晰。
- **遗留局限**：邮件为模拟发送，未接真实 SMTP；年级目前只在报名时校验，后续可补充活动开始时间、报名截止等公共规则的统一校验位置。
