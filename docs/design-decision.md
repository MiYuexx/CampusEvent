# 设计模式决策报告

## 1. 总体职责划分

| 模块/类 | 职责 |
| --- | --- |
| Activity | 活动领域数据：名称、类别、时间、地点、容量、报名方式 |
| Student | 学生领域数据：学生 ID、姓名 |
| Registration | 报名记录：关联活动与学生，记录状态与时间 |
| RegistrationService | 报名业务编排：重复校验、名额校验、状态流转、事件发布 |
| RegistrationPolicy（抽象） | 报名规则抽象：初始状态判定、是否可批准 |
| DirectPolicy / ReviewPolicy | 直接报名、审核报名两种策略实现 |
| EventDispatcher | 事件分发：订阅观察者，发布报名/审批/取消事件 |
| MessageObserver | 观察者：将事件写入站内消息，做重复通知防护 |
| Notification/Message | 站内消息持久化 |

依赖方向：Service 依赖策略抽象 `RegistrationPolicy`，不依赖具体策略；业务流程依赖事件分发接口，不直接调用消息写入。

## 2. 策略模式（设计任务 B）

### 抽象接口

`RegistrationPolicy` 定义两个稳定方法：

- `initial_status(activity, approved_count)`：提交报名时返回初始状态。
- `can_approve(activity, approved_count)`：审批时判断是否允许通过。

### 两种实现

- `DirectPolicy`：名额充足即返回 `APPROVED`；名额不足在初始提交阶段即拒绝。
- `ReviewPolicy`：提交返回 `PENDING`；是否可批准由审批阶段结合名额判断。

### 公共规则与策略责任划分

重复报名校验、「已通过」名额计数属于公共规则，放在 `RegistrationService` 统一处理；策略只负责该报名方式特有的状态判定。理由：

1. 重复校验与名额计数与报名方式无关，抽到策略中会造成两个策略重复实现。
2. 公共规则集中后，新增报名方式（如候补报名）只需实现策略接口，不必重写基础校验。

## 3. 观察者/事件通知机制（设计任务 C）

### 解耦结构

报名业务在状态流转后向 `EventDispatcher` 发布事件；`MessageObserver` 订阅事件并写入消息表。Service 不直接调用消息表写入。

### 事务边界与重复通知

- 通知失败在分发器中捕获，不向业务流程抛出，避免通知问题导致已合法提交的报名回滚；后续可将失败事件写入失败日志表留痕。
- 写入消息前按「学生 + 活动 + 内容」查重，同一状态事件只产生一条通知，避免重复通知。

## 4. SOLID 原则对照

- 单一职责：策略类只负责规则判定；观察者只负责消息写入；Service 只做业务编排。
- 开闭原则：新增报名方式或通知渠道时，扩展策略/观察者实现，不必修改主报名流程。
- 依赖倒置：Service 依赖策略抽象与分发接口，不依赖具体实现。
- 接口隔离：策略接口只包含报名规则所需方法；观察者接口只包含事件回调。

## 5. 模式成本与取舍

- 引入策略与观察者后，类数量增加、调用链路变长，简单需求下会比硬编码判断略复杂。
- 收益是规则与通知可独立扩展、独立测试；当报名方式或通知渠道继续增加时，扩展成本低于在主流程中堆叠 `if/else`。

## 6. 关键时序说明

### 6.1 直接报名时序

1. 学生提交报名请求。
2. Service 查询活动，校验是否已有有效报名。
3. 调用 `DirectPolicy.initial_status`，名额充足返回 `APPROVED`。
4. 写入报名记录并提交事务。
5. 发布 `REGISTERED` 事件，观察者写入站内通知。

### 6.2 审核型报名与批准时序

1. 学生提交报名，`ReviewPolicy.initial_status` 返回 `PENDING`，写入待审核记录。
2. 管理员对待审核记录执行批准。
3. Service 调用 `ReviewPolicy.can_approve` 复核名额；名额已满则批准失败。
4. 通过则状态改为 `APPROVED`，发布 `REVIEWED` 事件并写入通知；拒绝则改为 `REJECTED` 并写入通知。

### 6.3 取消报名时序

1. 学生取消本人待审核或已通过报名。
2. 状态改为 `CANCELLED`，已通过名额随之释放，统计同步更新。
3. 发布取消事件，写入站内通知。
